블로그가 ChatGPT 답변에 나오지 않는다고 바로 글의 구성을 바꿀 필요는 없습니다. 먼저 공개 페이지에 접근할 수 있는지 확인할 수 있습니다. 다만 접근이 된다는 사실과 실제 검색 답변에 인용된다는 사실은 별개입니다.

이 글은 공개된 봇 안내와 HTTP 응답을 이용한 점검 방법을 다룹니다. 검색 서비스의 비공개 순위 알고리즘을 설명하거나 특정 방문 수를 보장하지 않습니다.

## 어떤 접근을 허용할지 먼저 구분합니다

OpenAI는 `OAI-SearchBot`을 검색용, `GPTBot`을 모델 학습에 사용될 수 있는 콘텐츠 수집용으로 설명합니다. 두 설정은 독립적입니다. `ChatGPT-User`는 사용자의 요청에 따른 페이지 방문 등에 사용되며 자동 검색 크롤러의 설정과 같은 역할을 하지 않습니다. [OpenAI 봇 공식 안내](https://developers.openai.com/api/docs/bots)

검색용 수집은 허용하고 GPTBot의 수집은 거부하려는 경우에는 다음과 같은 규칙을 검토할 수 있습니다.

```text
User-agent: OAI-SearchBot
Allow: /

User-agent: GPTBot
Disallow: /
```

이 부분만 보고 사이트의 기존 `robots.txt` 전체를 덮어쓰면 안 됩니다. 기존 봇별 규칙과 사이트맵 선언을 함께 확인하세요. 실제로 비공개여야 하는 자료는 로그인과 접근 권한으로 보호해야 하며, `robots.txt`가 접근 통제를 대신하지는 않습니다.

공식 안내는 OAI-SearchBot을 거부한 사이트가 ChatGPT 검색 답변에 표시되지 않지만 탐색용 링크로는 나타날 수 있다고 설명합니다. 반대로 허용해도 인용이나 클릭이 보장되는 것은 아닙니다.

## 첫 번째: 공개 URL이 어떤 응답을 내는지 확인합니다

아래 명령은 macOS 또는 Linux에서 실행하는 읽기 전용 예시입니다. 자신의 실제 글 URL을 사용하세요.

```bash
curl --location --max-time 20 --silent --show-error \
  --dump-header page-headers.txt \
  --output page.html \
  'https://absianp.github.io/blog/2026-09-12-2025-gpt-aio-seo/'

curl --location --max-time 20 --silent --show-error \
  'https://absianp.github.io/robots.txt'
```

리다이렉트가 있으면 헤더 파일에 여러 응답이 남을 수 있으므로 마지막 응답까지 확인합니다. 최종 주소가 맞는지, HTTP 상태가 200인지, 200이어도 로그인·오류 화면을 반환하고 있지는 않은지 봅니다. `X-Robots-Tag` 같은 헤더도 기록하되 적용 방식은 해당 검색 서비스의 문서와 대조합니다.

이 명령이 200을 받는 것은 현재 실행한 환경에서 접근했다는 뜻입니다. 실제 검색 봇의 네트워크에서 동일하게 접근했다는 증거는 아닙니다.

## 두 번째: 받은 HTML 안에 본문이 있는지 봅니다

```bash
rg -n 'ChatGPT 검색 봇|OAI-SearchBot|canonical|noindex' page.html
```

본문의 고유한 문장 한두 개를 검색해 보세요. 제목과 빈 앱 컨테이너만 있고 본문이 없다면 어떤 방식으로 콘텐츠를 제공하는지 개발 환경에서 확인할 필요가 있습니다. 특정 서비스가 자바스크립트를 어떻게 처리하는지 추정해 단정하기보다, 초기 HTML에 읽을 내용이 있는지를 먼저 기록합니다.

`canonical`은 자신의 대표 글 주소를 가리키는지 확인합니다. 글을 이동하거나 통합했다면 예전 주소와 새 주소가 서로 모순되게 설정되지 않았는지도 봅니다.

## 세 번째: 차단이 있다면 발생 위치를 좁힙니다

| 관찰한 결과 | 다음에 볼 곳 |
|---|---|
| robots.txt에서 검색 봇을 거부 | 해당 봇에 적용되는 규칙과 운영자의 허용 의사 |
| 최종 응답 403·429 | 서버·CDN의 접근 로그와 차단 규칙 |
| 200이지만 오류 화면 | 애플리케이션 라우팅과 배포 결과 |
| HTML에 본문이 없음 | 정적 생성·서버 렌더링 등 콘텐츠 전달 과정 |

User-Agent에 봇 이름을 넣은 요청만 성공했다고 공식 봇 접근이 확인된 것은 아닙니다. User-Agent 문자열은 임의로 보낼 수 있으므로 방화벽에서 이름만 보고 무조건 허용하는 규칙도 피해야 합니다. 공식 봇 여부를 확인해야 한다면 운영사가 공개하는 IP 정보와 실제 요청 출처를 대조합니다.

GitHub Pages를 사용한다면 일반 웹 서버의 Nginx 접근 로그를 직접 읽는 방식으로 확인할 수 없습니다. 자신이 실제로 접근 가능한 호스팅 기능과 분석 도구 범위에서 증거를 모으세요.

## 접근, 인용, 방문은 따로 기록합니다

봇 요청 로그는 콘텐츠 수집의 흔적이고, 답변의 출처 링크는 인용의 흔적입니다. 사람이 그 링크를 클릭해 들어온 것은 또 다른 결과입니다. 셋을 한 숫자로 합치면 어디에서 변화가 생겼는지 알 수 없습니다.

JSON-LD나 `llms.txt`가 있다고 인용이 보장된다고 판단할 근거도 없습니다. Google은 자사 검색의 AI 기능에 특별한 추가 요구사항이 없으며 기본 검색 지침이 계속 적용된다고 안내합니다. 이 설명을 다른 서비스의 비공개 알고리즘까지 증명하는 근거로 확대해서는 안 됩니다. [Google AI 검색 기능 안내](https://developers.google.com/search/docs/appearance/ai-features)

점검 결과에는 확인 날짜, URL, 최종 HTTP 상태, 본문 유무, 적용 중인 봇 규칙을 남기면 됩니다. 실제 인용을 확인했다면 질문과 날짜, 답변에 표시된 출처 URL을 별도 기록하세요.
