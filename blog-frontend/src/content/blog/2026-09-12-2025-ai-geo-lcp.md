애드센스 신청을 앞두고 있다면 글의 길이보다 먼저 확인할 것이 있습니다. 글을 읽은 사람이 실제로 문제를 해결할 수 있는지, 수치와 설명에 근거가 있는지, 같은 내용을 제목만 바꿔 반복하지 않았는지입니다.

Google은 독창적인 콘텐츠와 사이트 이용성을 확인하도록 안내합니다. 특정 글 수, 글자 수, 이미지 수의 조합을 갖추면 승인된다는 공식은 제시하지 않습니다. [애드센스 사이트 준비 안내](https://support.google.com/adsense/answer/7299563?hl=ko)

## 첫 점검은 글 다섯 편을 직접 읽는 것입니다

홈에서 최근 글, 대표 글, 오래된 글을 섞어 고릅니다. 다섯 편은 작업을 시작하기 위한 표본이며 승인 기준이 아닙니다. 문제가 발견되면 같은 유형의 글까지 범위를 넓힙니다.

| 확인할 것 | 문제의 예 | 수정 방법 |
|---|---|---|
| 제목과 본문 | 설치 안내인데 설치 명령어가 없음 | 최소 예제와 실행·오류 확인 추가 |
| 독자에게 남는 답 | 장점만 나열하고 절차가 없음 | 필요한 준비물과 실제 순서 설명 |
| 수치의 근거 | 근거 없이 비용 절반·수익 몇 배 주장 | 측정 조건을 제시하거나 주장 삭제 |
| 최신 조건 | 지난 제도를 올해 기준처럼 소개 | 공식 출처에서 조건과 적용일 확인 |
| 글 간 중복 | 주제명만 바꾼 동일 본문 | 독자 질문별로 재작성하거나 통합 |

“직접 해보니”라는 말을 넣는다고 경험이 생기는 것은 아닙니다. 실제 사용 기록이 있다면 환경과 관찰을 쓰고, 문서 조사로 작성했다면 출처와 적용 범위를 제시합니다.

## 로그아웃한 화면에서 이동 경로를 확인합니다

워드프레스 관리자에게 보이는 페이지와 방문자에게 보이는 페이지는 다를 수 있습니다. 로그아웃한 브라우저에서 홈 → 카테고리 → 글 → 관련 글을 따라가 보세요. 글이 비어 있거나, 로그인 창에 막히거나, 존재하지 않는 주소로 이동하는지 확인합니다.

검색 공개를 원한다면 워드프레스의 검색 엔진 접근 설정과 SEO 플러그인의 `noindex` 설정도 살펴봅니다. 관리 화면에서 체크만 바꾸고 끝내지 말고, 실제 페이지 소스와 HTTP 응답에 어떤 값이 나가는지 확인해야 합니다. `noindex`는 검색 색인과 관련된 지시이며 애드센스 승인 여부와 동일한 개념은 아닙니다. [Google의 noindex 안내](https://developers.google.com/search/docs/crawling-indexing/block-indexing)

사이트 소개에는 누가 어떤 범위의 글을 쓰는지 사실대로 적습니다. 연락처는 실제 확인하는 경로를 사용합니다. 개인정보처리방침은 사이트가 실제로 사용하는 광고·분석 도구와 데이터 처리에 맞춰야 합니다. 내용과 다른 문구를 복사해 두는 것으로 끝내지 않습니다. [Google 게시자 정책의 개인정보 관련 안내](https://support.google.com/publisherpolicies/answer/10437794?hl=ko)

## 모바일에서는 글을 끝까지 읽어 봅니다

메뉴가 열리는지, 표가 옆으로 넘치는지, 코드가 잘리는지 확인합니다. 팝업이나 광고가 제목과 본문을 가리는지도 봅니다. 직접 촬영한 사진이나 설정 화면이 필요하다면 실제 자료를 준비하고, 이미지 설명에는 무엇을 보여 주는지 적습니다.

대표 이미지가 크다고 바로 캐시 플러그인을 여러 개 설치하지는 마세요. 먼저 이미지 크기와 파일 용량, 불필요한 외부 스크립트를 확인합니다. 캐시를 손볼 때는 로그인 화면이나 동적 페이지의 동작까지 고려해야 하므로, 모든 사이트에 동일한 서버 설정을 복사하는 방식은 피하는 편이 낫습니다.

## LCP는 읽기 성능을 보는 지표입니다

LCP는 화면의 큰 콘텐츠가 표시되는 시점을 측정하는 지표입니다. web.dev는 좋은 사용자 경험의 기준으로 2.5초 이하를 안내하며, 실제 방문의 75번째 백분위수를 모바일과 데스크톱으로 나누어 평가하도록 설명합니다. **이 수치는 애드센스 승인 기준이나 수익 보장 수치가 아닙니다.** [LCP 공식 설명](https://web.dev/articles/lcp)

[PageSpeed Insights](https://pagespeed.web.dev/)에서 모바일과 데스크톱 결과를 확인할 수 있습니다. 실사용자 데이터가 없는 사이트에서는 실험실 측정만 표시될 수 있습니다. 한 번 나온 점수를 실사용자의 전체 경험으로 해석하지 말고, 같은 페이지와 조건에서 변경 전후를 비교하세요.

글을 읽기 어렵게 만드는 큰 이미지나 화면 흔들림을 먼저 고친 뒤 다시 측정합니다. “LCP 1.2초를 만들면 48시간 안에 승인된다”처럼 성능과 비공개 심사 절차를 연결할 근거는 없습니다.

## 신청 전에 남길 기록

수정한 URL, 수정 이유, 공식 출처를 확인한 날짜, 모바일에서 확인한 결과를 적습니다. 아직 확인하지 못한 제도나 실행하지 않은 기술 예제도 구분해 두면 다음 검토가 쉬워집니다.

신청과 검토 상태는 애드센스 화면에서 확인합니다. 거절 사유가 표시되면 해당 사유와 실제 사이트를 대조해 수정 범위를 정하세요. 페이지 서식만 반복해서 바꾸기보다 독자에게 빠져 있는 답을 채우는 것이 편집의 중심입니다.
